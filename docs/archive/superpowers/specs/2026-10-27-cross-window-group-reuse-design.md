## Behavior

Prefer its current matching group, then a matching group in its current window ordered by first member index/group ID, then remote groups ordered by window ID/first member index/group ID. Return the chosen group's actual window ID. Create a group in the incoming window only when no eligible matching group exists. Do not merge pre-existing same-title groups, rename them, or move their members. Incoherent or relevant shared-group evidence stops work; it must not authorize creating a competing group.

Task007a remains authoritative: an existing eligible URL duplicate's live grouped or ungrouped location and after-anchor position win over every grouping rule. Keep the current duplicate anchor ordering, incoming tab identity/history, document checks, single-tab removal protocol, and normal/incognito isolation.

A foreground incoming navigation is one whose incoming tab is active in the first operation observation and whose source window is focused in corroborating attention evidence before placement. Capture this intent before any move. Foreground placement selects the incoming tab in the destination and focuses that window. An inactive incoming tab, an unfocused source, missing evidence, or conflicting initial observations authorizes no activation or window-focus operation. Never promote background intent because the tab becomes active later. Presentation applies to both rule-only placement and duplicate inheritance, including unchanged/same-window destinations where already-satisfied actions are no-ops.

Deliberate background placement must issue zero activation/focus calls and retain the active tabs and focus of surviving windows/tabs. Removing an active duplicate or emptying a source window can necessarily cause Chrome to select a successor; do not claim the removed tab/window can remain active/focused or invent restoration calls. Test ordinary background cases with surviving active spare tabs so native presentation preservation is asserted directly.

## Architecture

Omitted options retain the existing own-window contract; only production `planReplacement` passes `{scope:'all-normal-windows'}`. Production already supplies all-normal-window snapshots and the placement executor already moves the incoming tab before joining a remote group. Preserve the older group-placement service and its existing default-resolver tests. Do not build a second global executor.

Represent presentation separately from structural placement data. Add `PresentationState = Readonly<{ focusedWindowId: number | null; activeTabs: readonly Readonly<{ windowId: number; tabId: number }>[] }>` and `PresentationIntent = Readonly<{ kind: 'preserve' }> | Readonly<{ kind: 'foreground'; sourceWindowId: number; initial: PresentationState }>` in `src/planning/presentation.ts`. Its pure classifier `planPresentation(tabId: number, sourceWindowId: number, initiallyActive: boolean | undefined, state: PresentationState | undefined): PresentationIntent` requires unique coherent normal-window attention evidence and active/focused source agreement. The consumer captures `initiallyActive` from the first placement snapshot, corroborates it with `readPresentation()`, and passes intent into `planReplacement`; absent intent defaults to preserve for callers lacking attention evidence. Preserve active evidence in `PlacementSnapshot` without changing duplicate selection ordering.

Add narrow port operations `readPresentation(): Promise<PresentationState | undefined>`, `activateTab(tabId: number): Promise<void>`, and `focusWindow(windowId: number): Promise<void>`. The browser adapter reads populated normal windows; missing, ambiguous (including multiple focused windows), or unavailable initial attention evidence returns undefined and suppresses presentation while allowing valid core placement. Subsequent unavailable evidence revokes an already-foreground operation before closure. It calls exactly `tabs.update(id, {active:true})` and `windows.update(id, {focused:true})`. No synthetic navigation, tab recreation, URL updates, permission additions, or fire-and-forget promises. Existing grouping/title adapters retain their purposes.

Presentation is the final stage of the existing placement executor, **before** its successful placement receipt and all duplicate closure. Use the same serialized pending-write → full structural/document/attention preflight → native await → settlement → full verification → verified-phase protocol for `activate` and `focus` as for moves. First activate incoming if necessary, then focus destination if necessary, then verify both. A native activation reveals a collapsed destination group; no separate collapse mutation is needed. Any presentation failure or revoked foreground authority stops the replacement before closure. Do not roll back native partial effects or retry a native operation. This is smaller and safer than a separate post-closure presenter whose failure could follow irreversible removals.

## Attention authority and races

Check the captured attention state around asynchronous preflights and immediately before each mutation. Before moving a foreground winner, its source must still be focused and that winner active. Placement mutations that cannot change attention must preserve the receipt. A cross-window move may deactivate the incoming tab and select a source successor; accept only the known native transition in the affected source/destination windows after that issued move, then freeze the observed successor as the new attention receipt. Other windows' active selections must remain unchanged, and the source must remain focused. If the source disappeared, accept continuation only when destination focus is already observed; otherwise stop conservatively. Before activation/focus, recheck this receipt after the durable pending write and all document/snapshot awaits. Activation may change only destination selection; focus may change only the focused window. Verify expected changes after each awaited call.

Changing to another window/tab while an ordinary read, journal write, or document preflight waits revokes foreground presentation and prevents closure. An indistinguishable user action during Chrome's own move-induced selection, a switch away and back between observations, and the final check-to-native-call interval are unavoidable limits of these non-atomic APIs. Document those limits; do not introduce an unrelated broad activation-event tracker or pretend snapshots eliminate them.

The attention receipt remains authoritative through the durable `placed` checkpoint: after that write, verify the final foreground receipt once more before entering closure. After accepted placement/presentation, no further activation/focus commands occur. Duplicate cleanup then uses its existing document/snapshot/removal-lease guards; a later focus-only switch does not require attention-state tracking through each native removal. This keeps the data-safety protocol independent of subsequent browsing attention while preventing a stale presentation from granting initial closure authority.

A suspended/terminated worker with pending activation/focus is as uncertain as one with a pending move. Settlement bookkeeping failure keeps admission blocked. Presentation uncertainty never opens a path to duplicate removal.
